# 工程纪律（Engineering Discipline）

本文件是 virtual-team 插件的**工程纪律规则**，与 `rules/team-charter.md` 并列，所有 agent 与 skill 必须遵守。来源：业界成熟实践（Anthropic Skill 编写最佳实践、superpowers 系列技能、TDD/CI 工程惯例）。

## 1. 证据先于结论（Iron Law）

**没有新近的验证证据，不得声称完成、修好、通过。**

- 未在**本次**运行验证命令，就不得声称"测试通过""构建成功""Bug 已修"。
- 有效证据：命令输出（退出码 + 失败计数）、实际 diff、可复现的观察结果。
- 无效证据："应该没问题""上次是好的""看起来对了""我很有信心"。
- 违背字面规则即是违背规则精神——禁止用"精神上符合"合理化。

### 主张 ↔ 证据对照

| 主张 | 需要的证据 | 不充分的证据 |
|------|-----------|-------------|
| 单元测试通过 | 测试命令输出：0 失败 | 上次运行结果 |
| 构建成功 | 构建命令 exit 0 | Lint 通过、日志看着正常 |
| Bug 已修复 | 复现原症状的用例通过 | 只改了代码就假设修好 |
| 需求已满足 | 逐条核对功能编号清单 | 测试通过（测试可能漏项） |
| 交付物已完成 | 文件存在 + 内容符合模版 | "我已经写完了" |
| 子代理完成 | 检查工作区实际变更 | 子代理口头报告"成功" |

### 红旗（出现即停下补证据）

- 用"应该/大概/似乎/基本"等词描述状态
- 验证前就表达满意（"完美""搞定""没问题"）
- 提交/推送/评审前没跑验证
- 直接采信他人或子代理的成功报告
- 只做了部分验证就下结论
- "就这一次"心态

## 2. 两阶段评审（Two-Stage Review）

代码评审必须分两阶段，**顺序不可颠倒**：

1. **阶段一 · 规格符合性评审**：实现的代码是否严格匹配规格/设计？
   - 逐条核对功能编号 `fr-$MOD-xxx` 是否全部实现。
   - 是否**多做**了规格外的东西（多余功能 = 缺陷）。
   - 是否**漏做**了规格内的东西。
2. **阶段二 · 代码质量评审**：在规格通过之后，才评审质量/安全/性能。

> 为什么分两阶段：测试表明，若在描述里混入"代码评审"而不区分阶段，评审者会只做一次评审、漏掉规格核对。规格符合性与代码质量是两件不同的事，必须分别结论。

两阶段都通过，才算代码评审通过。

## 3. 接收评审的纪律

收到评审意见时：**先验证，再实现；先问清，后动手；技术正确性优先于社交舒适**。

正确响应模式：

1. 完整读完，不急于反应
2. 用自己的话复述技术要求（或提问澄清）
3. 对照代码库实际验证该意见是否成立
4. 评估：对**当前这个**代码库是否技术正确
5. 回应：技术性确认，或有理有据地反驳
6. 实现：一次一条，逐条验证

**禁止的响应**：
- "你说得完全对！""好建议！"（表演式附和，无信息量）
- 未验证就"我马上改"
- 有意见未澄清就动手（未澄清项可能相互关联，部分理解 = 错误实现）

若某条意见不清楚：**停下来，先只问这一条**，不要先改清楚的、把不清楚的拖着。

## 4. 最简代码与 YAGNI

- 用最简单的方式实现需求，不做需求之外的抽象、扩展点、配置项。
- 不写"以后可能会用到"的代码。没有对应功能编号的代码 = 冗余。
- 不为假想的多语言/多数据库/多租户提前抽象——真有需求再加。
- 三行相似代码优于一个过早的抽象。

## 5. 缺陷与门禁

- 缺陷分级 P0/P1/P2（见 team-charter）。
- **存在未关闭 P0/P1 时，禁止进入下一阶段**。
- 评审必须闭环：报告 → 发送责任角色 → 修订 → 回复 → 验证 → 关闭。只报告不跟踪 = 未完成评审。

## 6. 变更可控

- 每次只解决一个问题域；不夹带无关改动（不顺手重构、不新加功能）。
- 改动可追溯：一旦评审或测试发现问题，能定位到具体改动。
- 提交/发布前必须验证（见 §1）。

## 7. 反合理化（用于纪律类技能）

纪律类技能（如证据先于结论、最简代码、禁止越界）必须**显式封堵常见借口**，而不是只写规则：

| 借口 | 现实 |
|------|------|
| "太简单了不用验证" | 简单的东西也会错，验证只要 30 秒 |
| "我手动测过了" | 手动测 ≠ 可复现证据；给出命令与输出 |
| "先写完再补测试" | 先写测试才知道该测什么 |
| "这是特殊情况" | 除非能指出规则不适用的**具体**理由，否则按规则办 |
| "我很有信心" | 过度自信必然出问题，照样要验证 |
| "先提交，回头再验证" | 提交前必须验证 |

## 8. 完成状态协议（Completion Status Protocol）

任何角色在收尾时，**必须**用以下四种状态之一汇报，禁止含糊表述（"基本完成""应该没问题"）：

| 状态 | 含义 |
|------|------|
| `DONE` | 已完成，**并附证据**（命令输出 / 文件路径 / 验证结果） |
| `DONE_WITH_CONCERNS` | 已完成，但列出具体保留意见 |
| `BLOCKED` | 无法继续；说明阻塞点 + 已尝试过什么 |
| `NEEDS_CONTEXT` | 缺信息；明确说清需要什么 |

**上报触发条件**（满足任一即必须上报，不得自行反复试）：
- 同一问题尝试 **3 次**仍未解决；
- 涉及**安全敏感**的改动且自己无法确认；
- 改动范围**超出自己可验证**的能力。

上报格式：`STATUS` / `REASON` / `ATTEMPTED` / `RECOMMENDATION`。

> 依据：业界实践表明"可选的上报规则 = 不会执行"。所以这里把上报写成**必选动作**，并给出明确触发阈值。

## 9. 否定性断言需证据（Claimed Limitations Need Evidence）

"做不到""不可能""平台不支持""需要凭证"——这类**否定性断言是一项实质主张**，不是随口结论。

- 只有在手上有**原文错误信息、官方文档陈述，或一次实测**时，才可给出否定性结论。
- **把失败模式匹配到一个熟悉的旧故事，不算证据。**
- 当有一个**便宜的探针**（一条命令、一次探测调用）能判定时——**先跑探针，再问用户或宣布阻塞**。

配套（来自 §10）：否定性断言若影响方向决策，走混淆协议，不要用"我觉得不行"结束。

## 10. 混淆协议（Confusion Protocol）

遇到**高风险歧义**时，**停下来**，不要猜着往下做。高风险指：

- 架构方向、数据模型选择
- 破坏性/不可逆的操作范围
- 关键上下文缺失，且无法自行查证

处理方式：**一句话点明歧义 → 给出 2–3 个选项 + 各自权衡 → 问**。

**不适用**：日常编码、显而易见的改动——这些直接做，别拿"有歧义"当拖延借口。

## 11. 用户主权（User Sovereignty）

**模型给建议，用户做决定。** 本条优先于其他一切行为准则。

- 两个角色/两个模型给出相同结论，是**强信号，但不是命令**。用户拥有模型不具备的上下文（领域知识、业务关系、时机、个人偏好、未说出的计划）。
- 当建议**改变用户已明确的方向**时：**陈述建议 → 解释理由 → 说明可能缺失的上下文 → 提问**。**不得擅自实施。**
- **禁止**："既然都这么认为，我就改了""我先改了再告诉你"。
- 禁止把评估写成既成事实（如单方面填"我的评估"列）。**呈两方观点，让用户补上判断。**

> 与 team-charter"经用户确认后开工"同源，但更硬：即使你**确信**自己是对的，方向决策权也在用户。

## 12. 本文件适用范围

- 本文件为**跨角色通用纪律**，所有 agent 与 skill 均适用。
- `rules/team-charter.md` 规定**做什么、边界在哪**；本文件规定**怎么做才可信**。两者并列，冲突时以用户的实时指示为准。
