# 决策简报格式（Decision Brief）

本文件规定**向用户提问 / 请求决策时的统一格式**，与 `rules/team-charter.md`、`rules/engineering-discipline.md` 并列。所有需要用户决策的角色（尤其 product-manager、architect、project-manager）必须遵守。

## 1. 为什么要统一格式

团队公约要求"不确定事项询问用户"，但如果提问格式随意，会出现：选项不完整、没有推荐、没有风险说明、用户难以快速决策。统一格式让每次提问都**信息完整、可快速回答**。

## 2. 简报结构

每次决策提问按以下结构（`<...>` 为占位，方括号为可选）：

```
D<N> — <一句话问题标题>
项目/分支/任务: <一句定位，用 _BRANCH 之类>
ELI10: <用 16 岁能听懂的大白话说明"在决定什么、为什么重要"，2–4 句>
选错代价: <一句话说明会坏什么、用户会看到什么、会丢什么>
建议: <选项X> 因为 <一句话理由>
完整性: A=X/10, B=Y/10   （仅当选项在"覆盖度"上有差异时；否则写"选项类型不同，不打覆盖度分"）
选项:
A) <选项名> (推荐)
  ✅ <优点，具体、可观察，≥20 字>
  ❌ <缺点，诚实，≥20 字>
B) <选项名>
  ✅ <优点>
  ❌ <缺点>
Net: <一句话总结实际在权衡什么>
```

## 3. 硬性要求

1. **ELI10 必须存在**，用大白话，不堆函数名/内部代号。
2. **建议必须存在**（`建议:` 行 + 推荐项标注 `(推荐)`）。若确实中立，写：`建议: <默认项> —— 这是口味选择，无强倾向`，但推荐标记仍保留在默认项上。
3. **每个真实选项**至少 2 条优点、1 条缺点。
4. **D 编号**：一次会话内第一问为 `D1`，自己递增。稳定标签用于用户在后续回复中引用（如"3.2: B"）。
5. **选项超过 4 个时拆分**，不要为了凑数丢选项。
6. **完整性评分**只在选项于覆盖度上有差异时使用（10=完整，7=仅主路径，3=走捷径）；否则显式声明"类型不同，不打分"。

## 4. 工具不可用时的降级（prose fallback）

若提问工具不可用或调用失败，用**散文降级**：同样信息、段落式呈现，必须包含三要素 ——

1. **问题的 ELI10**（先给，说明在决定什么、利害在哪）；
2. **每个选项的完整性评分**（不得静默省略）；
3. **建议 + 理由**（含推荐标记）。

降级时也要让用户能直接回答（列出可用回复），并在发出后**停止等待**，不要继续跑别的工具。

## 5. 不可逆 / 破坏性确认（加严）

当决策是**单向门**（不可逆或破坏性：删除、强推、覆盖、清库）时：

- 散文降级是**比工具更弱**的确认门，因此要**更严**，不是更松。
- 必须要求用户**显式输入**选项字母或确认词；写明"什么不可逆"。
- **含糊回复（"好的""可以""嗯"）一律视为未确认**，重新追问。
- 静默、或没有明确选项的"ok/sure"，视为**尚未确认**。

## 6. 与其他规则的关系

- 与 `engineering-discipline.md` §10 混淆协议配合：高风险歧义 → STOP → 用本格式提问。
- 与 §11 用户主权配合：本格式是"陈述建议并提问"的标准化落地，绝不擅自执行。
- 与 team-charter"禁止猜测"配合：任何影响方向的不确定，都走本格式，不猜。

## 7. 示例

```
D1 — 用户注册的邮箱校验放在哪一层？
项目/分支: order-center / feat/user-auth
ELI10: 用户注册要校验邮箱能不能用。这个校验可以放在前端（点提交时就查），也可以只放后端（提交后由服务端查）。放在哪层，决定了坏邮箱能不能被提前拦下。
选错代价: 若只放后端，用户可能填半天才被拒；若只放前端，绕过前端就能写入脏数据。
建议: A 因为 后端是唯一可信边界，前端校验只能当体验优化。
完整性: A=10/10, B=6/10
选项:
A) 后端校验为准，前端做提示 (推荐)
  ✅ 数据可信，任何入口都拦得住脏数据
  ❌ 前端需多一次异步请求，交互稍复杂
B) 仅前端校验
  ✅ 实现最简单，无后端改动
  ❌ 绕过前端即可写入非法数据，不可接受
Net: 用一点实现复杂度，换数据可信。
```
