# 需求评审（requirement-review）

## 目的

评审业务分析说明书、需求规格说明书的质量，确保需求完备、准确、一致、可追溯。

## 执行者

`requirement-reviewer`（评审人另含**用户**）

## 输入

- `docs/PROJ_$PROJECT_NAME.md`
- `docs/requirements/overview.md`、`biz-$MOD.md`、`spec-$MOD.md`、`spec-nonfunc.md`、`dict.md`

## 输出

- `review/requirement/RV-REQ-xxx.md`

## 评审角度（8 项，逐项给结论）

1. 业务流程准确性、合理性，能否达到业务目标
2. 业务功能定义完备性，是否满足业务运行实际要求
3. 数据字典完整性，业务实体状态变化合理性
4. 业务需求一致性，是否存在矛盾
5. 业务模块划分合理性（高内聚、低耦合）
6. 非功能需求合理性（不遗漏、不过分）
7. 冗余、低价值需求筛查
8. 角色 / 业务流程 / 实体 / 功能 / 数据字典之间的相互关联合理性

## 报告格式

| 字段 | 说明 |
|------|------|
| 问题编号 | `RV-REQ-xxx-NN` |
| 级别 | P0 / P1 / P2 |
| 评审角度 | 1–8 |
| 位置 | 文件 + 章节（biz-xxx / fr-xxx / 实体） |
| 问题描述 | 具体 |
| 修改建议 | 可执行 |
| 责任角色 | product-manager 等 |
| 状态 | 待处理 / 已修复 / 已关闭 |

附**总体结论**：通过 / 不通过（列出阻塞 P0/P1）。

## 闭环

报告 → 发送产品经理 → 修改 → 回复 → 评审员验证 → 关闭。

## 检查清单

- [ ] 8 个角度逐项覆盖
- [ ] biz ↔ fr 覆盖矩阵已校验
- [ ] 结论明确（通过/不通过）
- [ ] 问题闭环

## 触发与边界

**该用**：需求产物完成、进入需求评审门禁时。

**不该用**：
- 评审设计/数据模型 → 用 `design-review` / `datamodel-review`
- 评审代码 → 用 `code-review`
- 评审项目整体可行性/验收 → 用 `accepting`

## 常见错误

- 只挑文字问题，不校验 biz ↔ fr 追溯（漏检缺功能）。
- 结论模糊，不给"通过/不通过"。
- 报告问题不给位置与责任角色，无法闭环。
