# 测试用例设计（case-design）

## 目的

制定测试方案，设计与功能点编号对应的测试用例，保证覆盖率。

## 执行者

`test-manager`（方案）/ `test-engineer`（用例）

## 输入

- `docs/requirements/`（功能点清单）
- `design/`
- `test/plan.md`（若已存在则增量补充）

## 输出（按模块分片）

**分片规则**：用例设计**按模块分片**——一个 test-engineer 实例只负责一个 `$MOD`，只产出本模块用例与结构化分片；多实例并行零交叉。

- `test/plan.md`（测试方案）
- `test/cases/CASE-xxx.md`（本模块测试用例）
- 本模块 `test/trace/case-$MOD.json` 分片（经 case-structure）

## 测试方案内容

1. 测试范围：覆盖哪些模块与功能编号；明确不测项及原因。
2. 功能测试策略：路径覆盖（正常/边界/异常）、数据驱动。
3. 非功能测试策略：性能（指标与压测方法）、安全（注入/越权/敏感信息）、兼容性。
4. 环境与基线要求。
5. 准入/准出标准。

## 用例格式（统一，`CASE-xxx` 必须与 `fr-$MOD-xxx` 关联）

用例是**静态资产**：步骤用 `${var}` 占位符引用数据（由数据单元提供），**不写死具体数据值**；执行结果（实际结果/结论/缺陷）由 `case-running` 落在 EXEC/BUG，**不回写用例**。

```
CASE-001
关联功能点: fr-user-auth-001
关联数据单元: TD-xxx（设计意图，最终以 case-structure 的 dataset_refs 为准）
类型: 功能 | 优先级: P1
前置条件: ...
操作步骤:
  1. 加载数据单元 TD-xxx（执行其 load_entry）
  2. 以 ${var_a} 执行被测操作
  3. 校验返回满足 ${expected_semantics}
预期语义: ...（描述"应验证什么"，具体 expected 在执行计划配对行落定）
```

## 覆盖要求

- **所有功能点都必须至少有一条对应用例**（含正常路径 + 关键边界 + 异常路径）。
- 设计用例时**同步识别数据需求**（什么场景底座能支撑本用例），为 `test-data-gen` 提供输入。
- 覆盖率矩阵**不由本技能手写**——由 `test-rebuild` 从结构化数据派生（单一真相）。

## 检查清单

- [ ] 测试方案通过用户确认
- [ ] 全部功能点被用例覆盖
- [ ] 用例格式统一、编号规范、步骤参数化
- [ ] 每条用例已标注数据需求（供 test-data-gen 生成）

## 触发与边界

**该用**：测试准备阶段，出方案与用例。

**不该用**：
- 执行用例 → 用 `case-running`
- 结构化存储与关联 → 用 `case-structure`
- 评估测试结果 → 由 test-manager 直接评估

## 常见错误

- 用例与功能点不关联（无法证明覆盖）。
- 只写正常路径，漏边界与异常。
- 步骤写死具体数据值（无法参数化、无法多数据集复用）。
- 在用例里填执行结果（结果属 EXEC，用例是静态资产）。
- 测试范围不写"不测项及原因"。
