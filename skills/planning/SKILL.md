# 立项（planning）

## 目的

实现项目的概要立项：描述项目轮廓、业务定位，形成可供评审的立项报告。

## 执行者

`project-manager`

## 输入

- 与用户的交互（项目构思、目标、约束）
- 已确认的项目基本要求（技术栈、用户数量、性能要求）

## 输出

- `docs/PROJ_$PROJECT_NAME.md`（模版：`templates/PROJECT.md`）

## 流程

1. **需求澄清**：向用户确认以下要素，不确定的必须提问，不得假设：
   - 项目名称 `$PROJECT_NAME`、一句话定位
   - 目标用户与使用场景
   - 核心业务价值（解决什么问题）
   - 技术栈与依赖约束
   - 用户规模、性能/安全/合规约束
   - 交付形态（Web / 桌面 / 服务 / 库）与里程碑预期
2. **可行性初判**：技术、资源、周期是否可行。
3. **风险登记**：列出技术风险与不确定项。
4. **编写立项报告**：严格按 `templates/PROJECT.md` 结构填写。
5. **提交评审**：交用户 + `project-reviewer` 做立项评审。

## 质量要求

- 立项报告必须包含：项目定位、范围（含**明确的不做项**）、目标用户、核心业务、技术栈、约束、里程碑、风险。
- 范围边界必须清晰，禁止"做大做大做强"式模糊描述。
- 每个不确定项要么有用户确认的答案，要么显式登记为待确认。

## 检查清单

- [ ] 项目定位一句话说清
- [ ] 范围含明确的不做项
- [ ] 技术栈与约束已与用户确认
- [ ] 里程碑可衡量
- [ ] 风险已登记
- [ ] 立项报告已提交评审

## 触发与边界

**该用**：项目从零启动、范围/约束/里程碑需要定下来、要产出立项报告时。

**不该用**：
- 项目已立项、要做业务建模 → 用 `business-analysis`
- 只做技术方案不涉及项目定位 → 用 `architecting`
- 项目已在进行中、只更新进度 → 由 project-manager 直接维护看板

## 常见错误

- 把"做大做强"式模糊描述当范围（必须写清**不做项**）。
- 技术栈拍脑袋定，不给约束依据。
- 未与用户确认就写立项报告（违背团队公约"禁止猜测"）。
