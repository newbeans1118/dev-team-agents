# 业务分析（business-analysis）

## 目的

从业务与用户角度描述系统需要实现的功能和业务实现流程，明确项目边界与模块划分。

## 执行者

`product-manager`

## 输入

- `docs/PROJ_$PROJECT_NAME.md`
- 与用户的交互

## 输出

- `docs/requirements/overview.md`（模版 `templates/BIZ-OVERVIEW.md`）
- `docs/requirements/biz-$MOD.md`（模版 `templates/BIZ-MOD.md`）

## 流程

1. **角色识别**：列出所有使用用户与角色，及其权限边界。
2. **边界与模块划分**：明确做什么 / 不做什么；划分系统高层模块 `$MOD`（模块间尽量独立）。
3. **业务建模**：每项业务给出独立编号 `biz-xxx`，并描述：
   - 业务说明
   - 前置条件
   - 业务流程（Mermaid 流程图 / 泳道图）
   - 业务处理
   - 业务输出
   - 涉及角色
4. **业务实体建模**：定义被管理的实体、实体描述、实体状态变化（Mermaid 状态图，含合法与非法迁移）。
5. **产出概览与分模块说明书**。

## 质量要求

- 模块划分高内聚、低耦合；模块间依赖显式列出。
- 每个业务必须有编号、前置条件、流程、输出、角色，缺一不可。
- 实体状态机必须闭环：每条状态迁移有触发条件与结果。
- 图形一律 Mermaid。

## 检查清单

- [ ] 角色清单与权限边界完整
- [ ] 模块清单 + 模块依赖图
- [ ] 所有 biz-xxx 要素齐全
- [ ] 业务流程图齐全（Mermaid）
- [ ] 实体状态机闭环

## 触发与边界

**该用**：把用户需求转成业务语言——角色、业务、实体、模块边界。

**不该用**：
- 要定义功能点 `fr-` 与规格 → 用 `requirement`
- 要设计技术架构 → 用 `architecting`
- 要有界面原型 → 用 `prototype`

## 常见错误

- 业务无编号或一个编号塞多个业务（`biz-xxx` 必须一业务一编号）。
- 状态机不闭环（缺少触发条件或非法迁移未列出）。
- 模块划分过粗/过细，模块间依赖未显式列出。
