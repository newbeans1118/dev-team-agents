# 产品发布（releasing）

## 目的

验收完成后，发布产品并交付用户，包括编译、打包、部署验证。

## 执行者

`release-engineer`

## 输入

- `src/`、`design/`
- 各阶段评审结论
- `test/report/`

## 输出

- `release/artifact/`（发布组件）
- `release/manual-release.md`、`release/manual-install.md`
- 部署验证记录 + 版本标签

## 流程

1. **全新 worktree 构建**：从 git 拉取分支到独立 worktree，从头构建（避免工作区脏状态污染）。
2. **编译**：按 `design/ARCH.md` 的构建系统编译。
3. **打包**：生成发布组件（含版本号、commit、依赖清单），归档到 `release/artifact/`。
4. **部署验证**：在实际目标环境部署，执行冒烟测试，记录验证命令与结果。
5. **标记发布状态**：
   - **测试版**：未经产品经理、测试经理、架构师、代码评审员联合确认。
   - **生产版**：经四方联合确认后，打上标签（`git tag`）。
6. **交付**：产出发布说明，交付用户。

## 约束（硬性）

- build 必须用全新 worktree，从 git 拉取分支从头构建。
- 发布组件必须**可复现**：记录版本、commit、构建命令、依赖版本。
- 未经四方联合确认的产物**只能标记为测试版**，不得作为生产版发布。
- 生产版必须打标签。

## 检查清单

- [ ] 全新 worktree 构建成功
- [ ] 发布组件归档且可复现
- [ ] 部署验证通过（附命令与结果）
- [ ] 发布状态正确标记
- [ ] 生产版已四方确认并打 tag

## 触发与边界

**该用**：验收通过后把产品构建、打包、部署、标记版本。

**不该用**：
- 还在开发/测试阶段 → 不发布
- 验收未通过 → 禁止发布生产版
- 只写安装/发布手册 → 用 `doc-writing`

## 常见错误

- 在脏工作区直接构建（必须全新 worktree）。
- 未经四方联合确认就标"生产版"（违规）。
- 发布物不可复现（未记录版本/commit/构建命令/依赖）。
- 部署不验证就宣称"能跑"（违背证据先于结论）。
