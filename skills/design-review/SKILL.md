# 设计评审（design-review）

## 目的

评审设计的正确性、合理性、完备性，产生评审文档。

## 执行者

`design-reviewer`（评审人另含**用户**）

## 输入

- `docs/requirements/`
- `design/ARCH.md`、`DATABASE.md`、`FUNC.md`、`DATASTRUCT-ALGORITHM.md`、`INTERFACE.md`、`LOGGER.md`

## 输出

- `review/design/RV-DESIGN-xxx.md`

## 评审角度

1. 技术选型合理性（满足需求、不过度设计、依赖必要）
2. 架构与组件设计正确性（分层、职责、交互闭环）
3. 数据库设计（模型规范、索引合理、DDL 与字典一致）
4. 功能设计完备性（功能编号全覆盖）
5. 接口设计（契约完整、异常路径定义）
6. 数据结构与算法（正确性、复杂度可接受）
7. 模块划分与依赖（低耦合、无循环依赖）
8. 日志设计（满足排障/审计）
9. 非功能设计落地（性能/安全/可扩展措施）
10. 可追溯性（设计条目 ↔ 功能编号）
11. **任务分解合理性**（评审 `design/DEV-TASKS.md`，在设计修订完成后进行）：以模块为单位切分、可独立开发与验收、依赖显式且**无环**、并行组划分正确、**功能编号全覆盖**、未越界写优先级/排期

## 报告格式

问题编号 `RV-DESIGN-xxx-NN`、级别（P0/P1/P2）、评审角度、位置（文件 + 章节 + fr 编号）、问题描述、修改建议、责任角色（architect）、状态。

须附**可追溯性校验结果**（功能编号 → 设计条目覆盖矩阵）；分解评审另附**功能编号 → 任务覆盖矩阵**与**依赖环检测结果**。

## 两轮时序

1. **第一轮**：评审设计文档（角度 1–10）。
2. **第二轮（分解评审）**：设计修订完成后，评审 `design/DEV-TASKS.md`（角度 11）。

分解评审**并入设计评审同一门禁**，不新增独立门禁；设计评审通过是分解评审的前置。

## 闭环

报告 → 发送架构师 → 修改 → 回复 → 评审员验证 → 关闭。

## 检查清单

- [ ] 11 个角度逐项覆盖
- [ ] 追溯矩阵无遗漏
- [ ] 分解评审：功能编号 → 任务覆盖矩阵 + 依赖环检测完成
- [ ] DDL 与数据字典一致
- [ ] 结论明确
- [ ] 问题闭环

## 触发与边界

**该用**：设计产物完成、进入设计评审门禁时。

**不该用**：
- 只评审数据库设计 → 用 `datamodel-review`
- 评审需求 → 用 `requirement-review`
- 评审代码 → 用 `code-review`

## 常见错误

- 只评审架构图，不校验"功能编号 → 设计条目"覆盖（漏检缺设计）。
- 结论不给"通过/不通过"。
- 建议不可执行（"性能要优化"无具体措施）。
