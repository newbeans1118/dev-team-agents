## 关于「并行子代理」机制的核实结论（供后续设计）

### 已确认事实
- **skill 无执行上下文、无返回值**：skill 是被主代理 Read 进来的指令文本；真正执行/派发的永远是主代理。
- **子代理有独立会话上下文 + 返回值**：派发时须给自包含输入（它看不到主对话），返回的只是最终报告（中间过程有损）。
- **插件的 `agents/*.md` 确实是「可被 spawn 的子代理类型」**：证据——本会话可用子代理列表含 tencent-docx 插件的 doc-converter / doc-formatter / doc-writer（该插件 `agents/` 下就是这三个 .md）。故 virtual-team 的 12 个角色安装后可被 spawn。
- **本会话实际派发工具名为 `Agent`**（参数 `subagent_type`），而 `project-manager.md` 的 tools 声明的是 `Task` —— **两者不一致，工具名待实测确认**。
- **当前只有 `project-manager` 声明了派发工具**，其余 11 个角色未声明 → 现状是主代理一人串行扮演全部角色，"12 角色并行"从未真正发生。
- **官方纪律**（tencent-docs-routing）：委派须**先走 skill，由 skill 指示 spawn**，不得绕过 skill 直接 spawn 子代理。
- **借鉴 gstack**：并行派发 = 一条消息里多个 Agent 调用并发；子代理 fresh context 避免先入偏见；输出结构化（JSON schema）便于主代理合并去重。

### 未验证（禁止假设）
- 子代理能否**再派子代理**（嵌套派发）——无证据。

## 实测：子代理嵌套派发（2026-10-11）

### 实验方法
主代理 spawn 一个 `general-purpose` 子代理（声明工具 `*`），指令其自检是否持有 `Agent` 工具并尝试实际 spawn 一个 `Explore`。

### 实测结果
- 子代理自报：**工具集中不含 `Agent` 工具**，`AGENT_TOOL_PRESENT: no`，无法启动子代理。
- 交叉核对系统子代理注册表：所有列出工具的子代理（statusline-setup / Explore / Plan / sheet-agent / doc-*）**无一包含 `Agent`**；仅 general-purpose 标为 `*`，而实测其无 `Agent`。
- **结论：嵌套派发（子代理再派子代理）在本环境不受支持。**

### 补充事实（推翻此前一处不准确说法）
- tencent-docx 三个 agent **没有 `tools:` 字段**，在会话中显示为 `(Tools:) 空` = **拥有全部工具**。
- 说明 **`tools:` 是白名单：写了即受限，不写即放行全部**。
- 我们插件 12 个角色**全部写了 `tools:` 且无一含 `Agent`**（仅 project-manager 写了 `Task`，与实际工具名不符）→ **我们的角色均不能派发**。

### 由此确立的架构结论
- **编排权唯一归属主代理**：所有运行期 spawn 只能由主代理执行。
- **PM 的"指派" = 规划期定责（写文件），非运行期 spawn**；PM 不需要 `Agent` 工具。
- 链条固定为：主代理 → spawn 角色子代理（各角色产出其交付物）→ 主代理汇总/派发下一环。
- **agent 文件里写"任务派发"指规划期定责，不得理解为运行期 spawn。**

## 【重要纠正】嵌套派发能力（推翻上一条结论）

### 上文错误结论
此前记录"子代理嵌套派发在本环境不受支持"——**该结论错误（过度推广）**。

### 正确事实（用户提供 CodeBuddy 官方文档 + 实测交叉验证）
1. **嵌套深度封顶 5 层**（主会话为第 0 层，不可配置）；超限时 Agent 工具返回错误并提示改用自身工具。
2. **子代理默认不持有 `Agent` 工具**；**只有定义中显式列出 `tools: Agent` 的 agent 才能继续嵌套**。
3. **并发上限**：每个根会话树默认最多同时执行 **20 个子代理**，可用环境变量 `CODEBUDDY_CODE_MAX_CONCURRENT_SUBAGENTS` 调整（正整数，不可关闭）。同步/后台/Team member/Skill/Workflow 的 AgentTask 共享该限制；任务结束即释放槽位。

### 实测交叉验证（与文档一致，非矛盾）
- `doc-writer`（无 tools 字段）实测工具集 22 个，**不含 `Agent`** → 印证"默认不授予"。
- `general-purpose`（标 `*`）实测亦无 `Agent`。
- 已安装插件中**无任何 agent 声明 `Agent`**。

### 修正后的结论
- **"无 tools 字段 = 拥有全部工具"的说法需修正**：`Agent` 是特殊工具，**默认不授予**，必须显式 `tools: Agent`。
- **PM 可以 spawn 子代理** —— 只要在 `project-manager.md` 的 `tools:` 中显式加入 `Agent`。用户方案成立。
- 待验证项：显式声明 `tools: Agent` 后是否真能 spawn（需已安装插件环境下实测）。

## 实测：并行子代理之间能否共享会话上下文（2026-10-11）

### 实验
spawn `general-purpose` 子代理，探测其是否持有 Task*/SendMessage 类工具、能否看到外部任务、能否创建任务。

### 实测结果
1. **子代理持有** `TaskCreate` / `TaskList` / `TaskUpdate`（yes）
2. **子代理不持有** `SendMessage` / `CreateColleague` / `TeamCreate`（no）
3. 子代理调用 `TaskCreate` 成功创建 `#22`
4. **子代理的 `TaskList` 能看到主代理在本会话创建的全部任务（#1–#21）** → 任务列表是**跨派发共享**的全局存储
5. 我们插件的 developer agent（backend/ui）tools 为：`Read, Write, Edit, Glob, Grep, Bash, AskUserQuestion` —— **不含任何 Task*/SendMessage**，也不含 `Agent`

### 结论：三层模型
| 层 | 是否共享 | 说明 |
|----|---------|------|
| **会话上下文**（对话历史 / LLM context） | ❌ 不共享 | 每个子代理独立 context，看不到彼此的 prompt、推理、读过的文件 |
| **agent 间消息**（SendMessage/Colleague/Team） | ❌ 不存在 | 子代理工具集中无此类工具 → 无法 peer-to-peer 协商 |
| **共享存储**（文件系统 + 全局 Task 列表） | ✅ 共享 | 文件是主要协作通道；Task 列表跨派发可见（需被授予 Task* 工具才可用） |

### 对并行开发的含义
- N 个 developer 实例**无法靠"对话"或"互相通信"协调**。
- 唯一可靠协作方式：**文件分治** —— 每个实例只写自己的模块目录，共享文件由上层串行化。
- 若给 developer 加 `TaskList`，他们能看到全局任务（含无关噪音），且会引入"谁能改任务状态"的权责问题；收益有限，暂不建议。
- **风险**：因无消息通道，两实例若改同一文件**无法协商** → 必须由派发方（主代理/PM）事前保证"一文件一写者"。

## 实测：子代理会话是否保留（2026-10-11）

### 实验设计（三步）
1. spawn 子代理 A，令其记住暗号 `SECRET_CODE = BANANA-7742` 与角色/编号 → 返回 Agent ID `agent-353ba8531234475a`
2. **用 `resume: agent-353ba8531234475a` 再次调用同一 agent**，考其是否记得
3. **对照组**：spawn 全新子代理（无 resume），问其是否知道该暗号

### 实测结果
| 组 | 结果 |
|----|------|
| **resume 组** | ✅ 精确复述 `BANANA-7742`、角色"测试员"、编号 `PROBE-SESSION-01`；自述**感知为一段连续对话** |
| **对照组（新实例）** | ❌ `RECALLED_SECRET: 不记得`；`CAN_SEE_OTHER_AGENT_CONTEXT: no` |

### 结论
1. **默认不保留**：每次 `Agent` 调用是**全新的隔离上下文**；子代理之间看不到彼此对话。
2. **可以保留**：通过 **`resume` + 上次返回的 Agent ID** 可续用同一会话，且上下文**跨两次独立工具调用仍存在**（即写入了持久存储，非仅单次调用内有效）。
3. 未验证边界：Agent ID 能否跨**顶层用户回合**或**会话重启**存活 —— 无证据，不假设。
4. 与上一条实测一致：子代理间**无消息通道**，会话隔离是默认态。

### 对插件的含义
- 并行派发 N 个 developer = **N 个互不共享上下文的独立实例**（现状）。
- 若要"同一实例连续做多任务"（保持上下文），必须**显式用 resume 传递 Agent ID** —— 这意味着**派发方需记录并管理 agent ID**，是个新的设计负担。
- 若派发方不记录 agent ID，每次调用都是全新的，上下文断档。
